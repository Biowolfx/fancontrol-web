# Plan: DSM Scheme Control + Node Management Fixes

## Problem Summary

Three related issues:

1. **DSM scheme control page missing**: When hwmon is unavailable (official Synology kernel), fan control falls back to `scemd.xml`, but the only UI is a single slider in the setup wizard. User wants a dedicated page with a table of all fan_config schemes (DUAL_MODE_LOW, DUAL_MODE_HIGH, etc.) showing temperature thresholds and fan speeds for each, with the ability to edit individual entries. Active scheme should be detected and highlighted.

2. **`showView()` broken for nodes**: `showView('nodes')` and `showView('node-detail')` don't toggle any DOM containers. The HTML also lacks `#nodes-grid` and `#node-detail-content` containers. Node management is incomplete.

3. **Agent discovery not working**: SSDP discovery infrastructure exists but agents aren't found. Likely causes: multicast TTL too low in Docker host network, or agent not running announcer in agent mode.

---

## Architecture Decisions

- **Two control paths, mutually exclusive per fan**: hwmon OR DSM, never both for the same fan. The `control_method` field on each fan dict distinguishes them (`'hwmon'` / `'dsm_scemd'`).
- **DSM page replaces slider**: When DSM mode is active, the main dashboard shows a DSM scheme editor instead of the standard fan cards with sliders.
- **Scemd.xml parsing must handle multiple formats**: Official Synology uses `<fan_config type="DUAL_MODE_LOW">` wrapping `<disk_temperature>` and `<cpu_temperature>` child elements. Custom ROMs may use flat `<disk_temperature>` elements. Parser must handle both.

Current code looks for `DUAL_MODE_LOW`/`DUAL_MODE_HIGH` as attributes on `cpu_temperature`/`disk_temperature` directly under root. This doesn't match the actual scemd.xml structure where these are children of `<fan_config type="DUAL_MODE_LOW">`.

      'hibernation_speed': 'UNKNOWN', # from fan_config @hibernation_speed
      'entries': [
        {
          'sensor_type': 'disk_temperature',  # element name
          'fan_speed': '20%40hz',             # raw fan_speed attr
          'action': 'NONE',                    # action attr
          'threshold_temp': '0',               # element text content
        },
        # ... more entries
      ]
    },
    # ... more schemes (DUAL_MODE_HIGH, etc.)
  ],
  'hw_version': None,
}

## Task 6: Fix agent discovery (SSDP)

**Files**: `agent/announcer.py`, `agent/client.py`, `server/discovery.py`, `templates/js/main.js`, `templates/index.html`

**Root cause analysis**: Agent announcer IS started (`agent/client.py:303-304`), server listener IS running (`socket_handlers.py:56-62`). But agent only does passive broadcast (every 60s). The `_handle_msearch()` function (line 67 of announcer.py) is never called, so server's active scan (`scan_for_agents()`) gets no responses. Passive listener may also fail silently if multicast bind fails in Docker host network.

### 6a. Start M-SEARCH responder in agent

In `agent/client.py:304`, after `start_announcer()`, also start `_handle_msearch()` in a daemon thread. This lets the server's active scan discover agents.

### 6b. Increase multicast TTL + add error logging

In `agent/announcer.py:48`, increase `IP_MULTICAST_TTL` from 2 to 4. In `server/discovery.py`, add explicit logging when `socket.bind()` or `IP_ADD_MEMBERSHIP` fails (currently errors are caught but may not surface).

### 6c. Add "Scan for agents" button in sidebar

In the node management area (bottom of sidebar), add a "Scan" button that calls `GET /api/nodes/discover` (exists at `routes.py:733-738`). Show discovered agents with Accept/Ignore buttons (existing `node:discovered` toast at `main.js:4764` already handles this, but manual scan provides a fallback).
